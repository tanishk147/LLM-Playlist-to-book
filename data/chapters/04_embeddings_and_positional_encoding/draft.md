## Token Embeddings, Positional Encoding, and Input Representations

By the time a raw sentence reaches a language model, it has already been transformed twice: first into tokens, then into integer token IDs. But integers are not a useful representation for a neural network. A model that sees the number 4,217 has no idea whether that ID is semantically close to ID 4,218 or to ID 12. To bridge this gap, we need *embeddings*—dense vectors that live in a continuous space where geometry encodes meaning. This chapter walks through the full journey from token IDs to the input representations that a transformer actually trains on, covering the embedding lookup table, the semantic properties of word vectors, why position information must be added separately, and how GPT combines token and positional embeddings into a single input tensor.

---

### The Three-Step LLM Input Pipeline

Before diving into the mechanics, it helps to see the big picture. The large language model workflow has three main steps: tokenizing input text into tokens, converting tokens into token IDs, and converting token IDs into token embeddings, which serve as input to training the model [c2514]. Token embeddings are also called vector embeddings or word embeddings, though "word embeddings" is not entirely accurate terminology because a token is a broader concept than a word [c2509, c2511]. The preferred term is *token embedding* precisely because tokens can be subwords, punctuation, or other units that do not map one-to-one to dictionary words.

[FIGURE: Three-stage pipeline: raw text → tokenizer → token IDs → embedding layer → token embedding vectors]

Token embeddings serve as the input to training large language models such as GPT [c2515]. Without them, the semantic relationship between related words like "dog" and "puppy" or "cat" and "kitten" would be lost entirely [c3275]. The full data pre-processing pipeline that feeds an LLM consists of four stages: tokenization, token embeddings, positional embeddings, and input embeddings [c3023]. We will work through each of the last three stages in this chapter.

### What Is a Token Embedding?

Token embeddings map words into a vector space where each word is represented as a vector with a fixed number of dimensions [c2528]. Intuitively, you can think of each dimension as a learned axis in a semantic space. A simple conceptual example: vector embeddings can be constructed by representing each word as a vector where each dimension corresponds to a semantic feature—for example, `has_a_tail`, `is_eatable`, `has_4_legs`, `makes_sound`, `is_a_pet` [c2521]. Real embeddings have hundreds of such dimensions, but the principle is the same: words that share properties end up with similar coordinates.

The key advantage of this representation is that vector embeddings can capture semantic meaning between words, whereas random number assignment and one-hot encoding cannot [c2523]. One-hot encoding, for instance, gives every word an orthogonal vector of the same length—there is no geometric relationship between "cat" and "kitten" in that scheme. Dense embeddings fix this by placing semantically similar words close together in the vector space.

#### Semantic Arithmetic

One of the most striking properties of well-trained embeddings is that vector arithmetic preserves semantic relationships. Word embeddings encode semantic properties such that masculine words (king, man) and feminine words (queen, woman) are distinguishable through vector operations [c2534]. Concretely, vector arithmetic on word embeddings preserves semantic relationships: $\text{king} + \text{woman} - \text{man} \approx \text{queen}$ [c2532, c2587]. Semantically unrelated word pairs such as "paper" and "water" have low similarity scores in Word2Vec embeddings [c2536], while the norm of the vector difference between two word embeddings is an indicator of how semantically close or distant the words are in meaning [c2538].

To see this in practice, the `word2vec-google-news-300` model (a 300-dimensional embedding trained on Google News) can be loaded and queried as follows:

# Source: [c2531]
```python
import gensim.downloader as api
model = api.load("word2vec-google-news-300")
word_vectors = model
print(word_vectors['computer'])
```

This prints a 300-dimensional vector for the word "computer." The analogy to convolutional neural networks is instructive: in CNNs, spatial features of an image are exploited before giving it as input for training, similar to how token embeddings work [c2585]. Both are learned feature representations that compress raw input into a form the network can reason about.

#### How Embeddings Are Learned

Token embeddings are created by training a neural network on textual data to learn vector representations where semantically similar words have similar vectors [c2524]. Token embeddings are generated by training a neural network to create vector representations for each word in the vocabulary [c2992]. Training data provides information about semantic relationships between words, which is used to optimize embedding weight parameters [c2549]. Importantly, token embedding values are learned and optimized during the LLM training process, not fixed at initialization [c3000]. Creating token embeddings for large vocabularies is computationally expensive, which is one reason why training large language models like GPT takes a huge amount of time [c2526].

### The Embedding Layer as a Lookup Table

In PyTorch, the mechanism that converts token IDs to embedding vectors is `torch.nn.Embedding`. It is a lookup table that stores embeddings of a fixed dictionary and size, used to store word embeddings and retrieve them using indices [c2555]. An embedding layer maps vocabulary IDs to dense vectors of a specified embedding dimension [c2575].

The embedding layer weight matrix is a lookup table that stores vector embeddings for each token ID in the vocabulary, with dimensions of `(vocabulary_size, embedding_dimension)` [c2993]. The first row of the embedding matrix is the vector for token ID 0, the second row is the vector for token ID 1, and so on [c2563]. The embedding weight matrix functions both as a matrix of weights for vector embeddings and as a lookup table for finding vector representations by token ID [c2568].

[FIGURE: Embedding weight matrix with vocab_size rows and embedding_dim columns; arrows from token IDs to their corresponding rows]

A token embedding matrix requires two quantities: the vector dimension (the size each token is projected to) and the vocabulary size (the number of unique token IDs) [c3300]. Creating the layer in PyTorch is straightforward:

# Source: [c2998]
```python
torch.nn.Embedding(num_embeddings, embedding_dim)
# Creates an embedding layer with num_embeddings rows and embedding_dim columns
# Stores embeddings of a fixed dictionary and size
```

For a small toy example with six tokens and three-dimensional embeddings:

# Source: [c2556]
```python
embedding_layer = torch.nn.Embedding(num_embeddings=6, embedding_dim=3)
```

You can inspect the underlying weight matrix directly:

# Source: [c2559]
```python
embedding_layer.weight
```

The embedding layer is a lookup operation that retrieves rows from the embedding layer weight matrix using token IDs [c3001]. An embedding layer lookup operation retrieves only the embedding vectors corresponding to the input IDs, without computing embeddings for unused vocabulary IDs [c2579]. This is an important efficiency property: even if the vocabulary has 50,000 entries, a forward pass only touches the rows that appear in the current batch.

You can pass multiple token IDs to the embedding layer in a single command to retrieve all their vector embeddings at once [c2571]. The embedding layer operates as a lookup mechanism that retrieves pre-stored vector representations indexed by token IDs [c3321]. An embedding layer is a lookup table that maps token IDs to their corresponding vector representations [c3317].

#### Mathematical Equivalence to a Linear Layer

There is a useful mathematical insight here: the output of `embedding(token_ids)` is equivalent to $X \cdot W^T$ where $X$ is the one-hot encoded input matrix and $W^T$ is the transposed weight matrix of a linear layer [c2581]. In other words, the embedding lookup is just a matrix multiplication in disguise—it is computationally equivalent to multiplying a one-hot vector by the weight matrix, which selects the corresponding row. PyTorch implements it as a direct index operation rather than a matrix multiply for efficiency, but the result is identical.

### Building the Token Embedding Layer for GPT

Now let us build the actual embedding layer we will use in our GPT implementation. Token embeddings for large language models are created by converting token IDs into embedding vectors using an embedding weight matrix [c2541].

For our implementation, input tokens are encoded into a 256-dimensional vector space for demonstration purposes [c3296]. The GPT-2 tokenizer has a vocabulary of 50,257 tokens [GAP: explicit citation for vocab_size=50257 from the playlist]. With a vocabulary size of 50,257 and an embedding dimension of 256, the layer is created as follows:

# Source: [c3003]
```python
vocab_size = 50257
embedding_dim = 256
token_embedding_layer = torch.nn.Embedding(vocab_size, embedding_dim)
# Creates embedding matrix with 50257 rows and 256 columns
```

For reference, the general pattern is:

# Source: [c2577]
```python
embedding = torch.nn.Embedding(vocab_size, embedding_dim)
# Example: torch.nn.Embedding(4, 5) creates a 4x5 embedding matrix
```

The token embedding weight matrix for GPT-2 has dimensions of vocabulary size (rows) by vector dimension (columns); for GPT-2, this is 50,257 rows by 768 columns [c2590]. Our demonstration uses 256 dimensions rather than 768, but the structure is identical.

Each token in the input batch is converted to a single 256-dimensional embedding vector [c3320]. Every token ID in a batch is converted into a vector of size 256 [c3339].

### The Data Loader: Feeding Batches to the Embedding Layer

Before embeddings can be computed, we need a mechanism to produce batches of token IDs. A data loader is a PyTorch tool that processes data by creating input-output target pairs using a sliding window approach [c2980].

Input-output pairs for LLM training are constructed based on context size, where each pair contains multiple prediction tasks corresponding to predicting the next word at each position [c2978]. In a data loader implementation, the input tensor `X` contains rows representing input contexts, and the target tensor `Y` contains corresponding prediction targets which are the input shifted by one word [c2981].

### The Problem with Token Embeddings Alone

Here is a critical limitation: token embedding does not take into account the position of words in a sequence, so identical words at different positions receive the same embedding vector [c3006]. In token embedding, the same token ID always maps to the same vector representation regardless of its position in the input sequence [c3277].

To see why this matters, consider the sentence "The dog bit the man" versus "The man bit the dog." The token IDs for "dog," "man," and "bit" are identical in both sentences, so a pure token embedding would produce the same set of vectors for both—even though the sentences have opposite meanings. Token embeddings alone do not encode positional information about where words appear in a sentence [c2594].

It is therefore important to inject additional position information to the large language model along with capturing semantic meaning through token embeddings [c3280]. Positional encoding is the final step in LLM data pre-processing that encodes information about the position of tokens in a sequence [c3276]. Positional encoding is a technique that injects additional positional information into large language models to complement token embeddings [c3008].

---

### Positional Encoding: Two Philosophies

There are two broad families of positional encoding. Absolute positional embeddings and relative positional embeddings are two different approaches to encoding position information [c3348]. Both absolute and relative positional embeddings enable large language models to understand the order and relationship between tokens, leading to more accurate and context-aware predictions [c3287].

#### Absolute Positional Encoding

In absolute positional embedding, the same token receives different final embeddings when it appears at different positions in the sequence because different positional embeddings are added to the same token embedding [c3283]. Each position in the sequence gets its own unique vector, and that vector is added to the token embedding at that position.

Absolute positional encoding is well-suited for tasks where fixed order of tokens is crucial, such as sequence generation [c3011]. GPT models (GPT-3, GPT-4) use absolute positional embeddings that are optimized during the training process [c3290]. GPT uses absolute positional encoding [c3012].

#### Relative Positional Encoding

Relative positional encoding emphasizes the relative distance between tokens rather than their absolute positions in the sequence [c3010]. Relative positional encoding is suitable for tasks like language modeling or long sequences where the same phrase can appear in different parts of the sequence [c3013]. Relative positional encoding allows models to generalize better to sequences of varying lengths, even if the model was trained on sequences of different lengths [c3285].

#### The Original Sinusoidal Formulation

The original "Attention Is All You Need" paper introduced a fixed, formula-based positional encoding using sine and cosine functions. The terms positional encoding and positional embedding are used interchangeably to refer to vectors in a higher dimensional space [c3295]. The sinusoidal formulas are:

$$PE_{(pos,2i)} = \sin\!\left(\frac{pos}{10000^{2i/d_{\text{model}}}}\right)$$ [c3292]

$$PE_{(pos,2i+1)} = \cos\!\left(\frac{pos}{10000^{2i/d_{\text{model}}}}\right)$$ [c3293]

where $pos$ is the position in the sequence and $i$ is the dimension index. These formulas produce a unique, deterministic vector for each position without any learned parameters.

GPT, however, does not use this fixed formula. Instead, it uses *learned* positional embeddings—the positional vectors are initialized randomly and then optimized during training, just like the token embeddings themselves.

### GPT's Learned Positional Embeddings

In our GPT implementation, the positional embedding layer is structured analogously to the token embedding layer. The size of the positional embedding matrix is determined by the context length (number of positions) and the embedding dimension [c3015].

The number of positional embedding vectors needed equals the context length, with one vector for each position [c3341]. Only four positional embedding vectors are needed, one for each position (first, second, third, fourth) in the sequence [c3328]—assuming a context length of four for this example. The positional embedding matrix has shape `4 by 256`, where 4 is the sequence length and 256 is the embedding dimension, with one 256-dimensional vector per position [c3333].

Positional embedding matrix values are initialized randomly, similar to token embedding initialization [c3021]. Both token embedding and positional embedding values must be optimized during the training process of large language models [c3022].

To generate positional indices for a sequence of length `max_length`, PyTorch's `torch.arange` is used:

# Source: [c3329]
```python
torch.arange(max_length) creates a sequence of integers from 0 to max_length-1, used to index into the positional embedding lookup table.
```

Passing positions 0, 1, 2, and 3 to the positional embedding lookup table generates four 256-dimensional positional embedding vectors [c3331]. The same four positional embedding vectors are reused across all input sequences in a batch because positions are identical across sequences [c3327].

### Combining Token and Positional Embeddings

With both the token embedding layer and the positional embedding layer in place, the final input representation is their sum. Positional embeddings are added to token embeddings using Python broadcasting, where the same positional embedding vectors are added to each row of the token embedding matrix [c3342].

Token embeddings have shape `8 by 4 by 256` and positional embeddings have shape `4 by 256` [c3017]. When adding token embeddings and positional embeddings in Python, broadcasting converts the `4 by 256` positional embedding tensor into `8 by 4 by 256` by duplicating values eight times [c3018]. The same positional embedding values are added to each row of the token embeddings across all 8 batches during the broadcasting operation [c3335].

[FIGURE: Broadcasting diagram: (4,256) positional embedding tensor expanded to (8,4,256) and added element-wise to (8,4,256) token embedding tensor]

Intuitively, this means every sequence in the batch gets the same positional "correction" applied to its token vectors. The first token in every sequence gets the same positional vector added to it, the second token gets the second positional vector, and so on. The result is an input embedding tensor of shape `(batch_size, context_length, embedding_dim)` where each position in each sequence has a unique representation that encodes both *what* the token is and *where* it appears.

In absolute positional embedding, the same token receives different final embeddings when it appears at different positions in the sequence because different positional embeddings are added to the same token embedding [c3283]. This is exactly the property we need: "dog" at position 0 and "dog" at position 3 will have different input embeddings, allowing the model to distinguish them.

### The Complete Pre-Processing Pipeline

Let us now assemble the full picture. The LLM data pre-processing pipeline consists of four stages: tokenization, token embeddings, positional embeddings, and input embeddings [c3023].

[FIGURE: Full pipeline diagram: raw text → tokenizer → token IDs → token embedding layer → token embeddings (8×4×256) → add positional embeddings (4×256, broadcast) → input embeddings (8×4×256) → transformer]

Here is a summary of the key components and their shapes for our demonstration configuration:

| Component | Shape | Notes |
|---|---|---|
| Token IDs | `(batch_size, context_length)` | Integer indices into vocabulary |
| Token embedding layer | `(50257, 256)` | Learned weight matrix |
| Token embeddings | `(8, 4, 256)` | One 256-d vector per token per sequence |
| Positional embedding layer | `(context_length, 256)` | Learned weight matrix |
| Positional embeddings | `(4, 256)` → broadcast `(8, 4, 256)` | One 256-d vector per position |
| Input embeddings | `(8, 4, 256)` | Token + positional, fed to transformer |

The `torch.nn.Embedding` API is the same for both layers:

# Source: [c3303]
```python
torch.nn.Embedding(num_embeddings, embedding_dim) creates an embedding layer that stores embeddings of a fixed dictionary and size, functioning as a lookup table that retrieves embeddings using token indices.
```

Both layers start with random weights and are jointly optimized during training. The gradient signal from the language modeling objective flows back through the transformer, through the addition operation, and into both embedding matrices simultaneously.

### Why This Design Works

It is worth pausing to appreciate why the additive combination of token and positional embeddings is a sensible design choice.

First, the addition is parameter-free at inference time—no extra weights are needed to combine the two signals. The model learns, through training, to use the positional dimensions of the embedding space to encode order information, and the remaining dimensions to encode semantic content. In practice, the two types of information become entangled in a way that the attention mechanism can exploit.

Second, the lookup-table design for both embedding types is efficient. The embedding layer is a lookup operation that retrieves rows from the embedding layer weight matrix using token IDs [c3001]. An embedding layer lookup operation retrieves only the embedding vectors corresponding to the input IDs, without computing embeddings for unused vocabulary IDs [c2579]. For a vocabulary of 50,257 tokens, this means a forward pass through the embedding layer touches at most `batch_size × context_length` rows—a tiny fraction of the full matrix.

Third, learned positional embeddings (as used in GPT) are more flexible than fixed sinusoidal encodings. GPT models (GPT-3, GPT-4) use absolute positional embeddings that are optimized during the training process [c3290]. The model can discover whatever positional representation is most useful for its specific training distribution, rather than being constrained to a hand-designed formula.

### Summary

This chapter has traced the path from raw token IDs to the input representations that feed a transformer. The key ideas are:

1. **Token embeddings** convert integer token IDs into dense vectors by looking up rows in a learned weight matrix [c2993, c3317]. The matrix has shape `(vocab_size, embedding_dim)` and is optimized during training [c3000].

2. **Semantic geometry** emerges from training: similar words cluster together, and vector arithmetic encodes relationships like $\text{king} - \text{man} + \text{woman} \approx \text{queen}$ [c2532].

3. **Token embeddings alone are position-blind**: the same token ID always produces the same vector regardless of where it appears in the sequence [c3006, c3277].

4. **Positional embeddings** inject order information by adding a position-specific vector to each token embedding [c3008]. GPT uses learned absolute positional embeddings [c3012, c3290].

5. **The input embedding** is the element-wise sum of the token embedding and the positional embedding, combined via broadcasting across the batch dimension [c3342, c3018].

6. **Both embedding matrices** are initialized randomly and optimized jointly during LLM training [c3021, c3022].

In the next chapter, we will see how these input embeddings flow into the self-attention mechanism, where the model learns to relate tokens to one another across the full context window.
